## Overview

This notebook workflow provides an interactive proofreading and validation interface for segmented dendritic spines. It compares a spiny morphology generated by the OBI skeletonization workflow with the corresponding source electron-microscopy mesh.

The workflow is designed for a reviewer who needs to:

- select a project, EM dataset, and skeletonized morphology;
- inspect only morphology sections that contain segmented spines;
- decide whether a section contains spines that were missed by segmentation;
- inspect every segmented spine in the selected section;
- record common segmentation defects;
- classify each spine as **Valid** or **Invalid**;
- capture visual evidence of the reviewed geometry;
- save and restore progress automatically;
- generate a PDF analysis report; and
- register the validation results and report.

The interface is implemented as an interactive Jupyter widget layout backed by a K3D WebGL 3D viewer. The validation state is persisted in a CSV file so that an assessment can be resumed after the notebook is closed or restarted.

> **Important:** Registration is currently allowed even when the assessment is incomplete. The registration output records the current validation state, including validated and remaining sections and spines. Reviewers should normally complete the assessment before registering unless an intentionally partial assessment is required.

## End-to-end workflow

The complete workflow consists of the following stages:

1. **Authenticate with OBI.** Select the configured environment and project context.
2. **Select an EM dataset.** Choose an accessible electron-microscopy dense-reconstruction dataset.
3. **Select a morphology.** Choose a skeletonized morphology derived from the selected dataset, or provide a platform morphology ID manually.
4. **Download the inputs.** Export the spiny morphology as HDF5 and download its source mesh as GLB.
5. **Launch the validator.** The tool loads the HDF5 morphology and GLB mesh and creates the interactive viewer.
6. **Review each spiny section.** Decide whether the section has missing segmented spines.
7. **Review each segmented spine.** Record the five defect categories and assign Valid or Invalid.
8. **Use automatic navigation.** After a validity decision, the next unvalidated spine is selected automatically. Completed sections advance to the next section.
9. **Capture evidence.** Save section-level or spine-level screenshots as required.
10. **Generate the report.** Create the analysis PDF from the current CSV state and saved visual evidence.
11. **Register the assessment.** Stage the validation CSV and analysis PDF, create the registration archive, and upload it through the registration helper.

The sequence is resumable: validation changes are written asynchronously to disk, and an existing validation CSV is restored when the validator starts.

## 1. Input selection and data loading

### 1.1 Authenticate and select a project

The canonical notebook begins by importing the OBI helper and authenticating:

```python
from pathlib import Path
import importlib
import sys

sys.path.insert(0, str(Path("lib")))
importlib.invalidate_caches()

import obi
env, token, project_context = obi.authenticate()
```

The authentication helper:

- resolves the configured OBI environment;
- requests a DAF authentication token;
- resolves the projects available to the authenticated user; and
- returns the environment, token, and project context used by later queries.

The selected project determines which EM datasets and derived morphologies are available to the notebook.

![Placeholder: OBI project/environment selection widget](docs/images/placeholder-project-selection.png)

### 1.2 Select an EM dense-reconstruction dataset

Display the accessible EM datasets with:

```python
client, sel_em = obi.display_datasets(
    env=env,
    token=token,
    project_context=project_context,
)
```

The dataset dropdown is populated from `EMDenseReconstructionDataset` entities available through the authenticated OBI client. Select the dataset from which the skeletonized morphology was derived.

Some datasets may not contain accessible skeletonized morphologies. If the morphology list is empty, select another dataset or run the skeletonization workflow on the platform first.

![Placeholder: EM dataset dropdown with an example selected dataset](docs/images/placeholder-dataset-selection.png)

### 1.3 Select a neuron morphology

The canonical workflow supports two selection modes:

#### Interactive morphology selection

Leave the manual ID at its placeholder value:

```python
neuron_id = "PASTE ID IN HERE"
sel_nrn = obi.display_neurons(
    client=client,
    sel_em=sel_em,
    neuron_id=neuron_id,
)
```

The notebook queries morphologies derived from the selected EM dataset and displays them in a second dropdown.

#### Manual morphology ID

Alternatively, replace the placeholder with the **OBI platform morphology ID**. This is not the EM `pt_root_id` or the neuron ID embedded in an asset filename. The platform ID can be copied from the **Data** section of the OBI virtual labs.

```python
neuron_id = "<OBI_PLATFORM_MORPHOLOGY_ID>"
sel_nrn = obi.display_neurons(
    client=client,
    sel_em=sel_em,
    neuron_id=neuron_id,
)
```

When a real ID is supplied, `display_neurons()` returns `None` and `download_data()` uses the notebook-level `neuron_id` variable.

![Placeholder: derived morphology dropdown and manual morphology-ID instructions](docs/images/placeholder-morphology-selection.png)

### 1.4 Download the morphology and source mesh

Run:

```python
morphology_path, mesh_path = obi.download_data(
    client=client,
    sel_nrn=sel_nrn,
)
```

The helper:

1. exports the selected spiny morphology to an HDF5 file;
2. resolves the source EM mesh associated with the morphology;
3. downloads the first mesh asset as a GLB file; and
4. returns the two local paths required by the validator.

The resulting files normally have the following form:

```text
<neuron_root>.h5
<neuron_root>.glb
```

### 1.5 Local/replay notebook

`analysis_noteboo_local.ipynb` skips authentication, dataset selection, morphology selection, and downloading. It directly calls the validator with local paths similar to:

```python
from pathlib import Path
import importlib
import sys

lib_dir = Path("lib")
sys.path.insert(0, str(lib_dir))
importlib.invalidate_caches()

import validate_spines_core
validate_spines_core = importlib.reload(validate_spines_core)

mesh_path = "/scratch/data/skeletonizations/<neuron_root>.glb"
morphology_path = "/scratch/data/skeletonizations/<neuron_root>.h5"

validate_spines_core.validate_spines(
    morphology_path=morphology_path,
    mesh_path=mesh_path,
)
```

Update both paths before running the local notebook. The morphology and mesh must correspond to the same neuron and source reconstruction.

## 2. Launching the interactive validator

The validator can be launched directly once both input files are available:

```python
import importlib
import validate_spines_core

validate_spines_core = importlib.reload(validate_spines_core)
validate_spines_core.validate_spines(
    morphology_path=morphology_path,
    mesh_path=mesh_path,
)
```

At startup, the tool:

- loads the spiny morphology;
- loads the source mesh vertices;
- identifies sections that contain one or more segmented spines;
- samples the global mesh for an always-visible context view;
- creates the K3D viewer and widget controls;
- checks for an existing validation CSV;
- restores saved section and spine decisions; and
- loads the first spiny section.

The startup summary reports the total number of morphology sections, the number of sections containing spines, the total spine count, the number of displayed mesh vertices, and the average number of spines per spiny section.

## 3. Viewer and layout

The interface is organized into three review columns and a projection-control area.

### 3.1 Section Navigation column

This column contains:

- the section selector;
- **Prev Section** and **Next Section** buttons;
- the **Missing Spines** button; and
- the **No Missing Spines** button.

Only sections with one or more segmented spines are included in the section selector. Each option is labeled with its section ID, spine count, and progress state, for example:

```text
Section 12 (18 spines)
Section 13 (7 spines) [4/7]
Section 14 (11 spines) [Done]
```

### 3.2 Spine Navigation and Analysis column

This column contains:

- the spine selector;
- **Prev Spine** and **Next Spine** buttons;
- five defect-analysis rows; and
- the **Valid** and **Invalid** classification buttons.

Each spine option displays its local ID, global ID, and current status:

```text
Spine 0 (Global ID 245) [NOT SET]
Spine 1 (Global ID 246) [VALID]
Spine 2 (Global ID 247) [INVALID]
```

### 3.3 Status, evidence, and assessment column

This column contains:

- the current section and spine status;
- section and overall progress counters;
- the **ScreenShot** button;
- the **Generate Report** button;
- the **Register** button; and
- report and registration status messages.

### 3.4 Projection and background controls

The viewer includes six orthographic projection buttons:

- **XY** and **-XY**;
- **XZ** and **-XZ**; and
- **YZ** and **-YZ**.

Each projection button includes a small axis-triad icon. The standard axis convention is used:

- X axis: red;
- Y axis: green; and
- Z axis: blue.

The **Black Background** button toggles the K3D canvas between a white and black background. After activation, the button label changes to **White Background**, indicating the action that will occur on the next click.

![Placeholder: viewer controls showing the three navigation columns, projection buttons, and background toggle](docs/images/placeholder-viewer-controls.png)

## 4. Section selection and section review

### 4.1 Selecting a section

A section can be selected in three ways:

1. choose it from the section dropdown;
2. click **Prev Section**; or
3. click **Next Section**.

Section navigation wraps around. From the first section, **Prev Section** moves to the last spiny section. From the last section, **Next Section** returns to the first spiny section.

When a new section is selected, the viewer:

1. clears the previous section’s local point cloud, spine meshes, centerline overlay, and bounding box;
2. focuses the camera on the selected branch;
3. displays the selected section centerline;
4. loads the section’s spine meshes asynchronously;
5. shows the local source-mesh point cloud; and
6. refreshes the status labels, dropdowns, and analysis table.

If a user changes sections while a previous section is still loading, the stale load is cancelled or ignored so that outdated geometry is not displayed over the newly selected section.

![Placeholder: selected section highlighted in red with all segmented spines visible](docs/images/placeholder-section-selection.png)

### 4.2 Section-level missing-spine decision

Before reviewing individual segmented spines, inspect the complete section against the source mesh and decide whether the segmentation missed any real spines.

Click one of:

| Button | Meaning | Stored value |
| --- | --- | --- |
| **Missing Spines** | At least one spine appears in the source mesh but is not represented by a segmented spine. | `missing` |
| **No Missing Spines** | No missing segmented spine was identified in the section. | `no missing` |

The section-level decision:

- is saved to the validation CSV;
- updates the section selector status; and
- automatically focuses the first spine in the current section.

This decision is independent of the validity of the displayed segmented spines. Marking a section as having missing spines does not automatically mark every displayed spine as Invalid.

![Placeholder: section-level review showing Missing Spines and No Missing Spines buttons](docs/images/placeholder-missing-spines-buttons.png)

## 5. Spine selection and visual inspection

### 5.1 Selecting a spine

A spine becomes explicitly selected when the reviewer:

- chooses a spine from the spine dropdown;
- clicks **Prev Spine** or **Next Spine**; or
- clicks a section-level missing-spine decision, which focuses the first spine.

The selected spine is shown with:

- a red bounding box;
- a camera focused on the spine bounds; and
- its assigned saturated palette color.

All other spines in the section are dimmed to gray after a specific spine is selected. Before a specific spine is selected, all displayed spines retain their distinct palette colors so the section can be reviewed as a group.

The selected spine’s local and global IDs remain visible in the spine dropdown and status area.

![Placeholder: selected spine inside a red bounding box with surrounding spines dimmed](docs/images/placeholder-selected-spine.png)

### 5.2 Mouse controls

The K3D viewer uses trackball navigation:

- **Rotate:** left-click and drag;
- **Zoom:** scroll;
- **Pan:** hold `Shift` and use the middle mouse button.

The projection buttons provide a quick way to return to a known orthographic view when free rotation makes the geometry difficult to interpret.

## 6. Spine defect analysis

Every explicitly selected spine has five analysis categories. Each category provides **Yes** and **No** buttons.

| Analysis | Select **Yes** when... | Select **No** when... |
| --- | --- | --- |
| **False Positive** | The displayed object is not a real spine and is likely a segmentation artifact. | The displayed object corresponds to a real spine. |
| **Incomplete Spine** | The segmented geometry represents only part of the real spine or is missing geometry. | The spine geometry appears complete. |
| **Falsely Extended** | The segmentation extends beyond the actual spine or includes unrelated geometry. | The segmented geometry stays within the actual spine. |
| **Merged Spine** | Two or more distinct spines have been incorrectly combined into one segmented object. | The object represents one spine without an apparent merge. |
| **Split Spine** | One real spine has been incorrectly divided into multiple segmented objects. | The object is not a split representation of one spine. |

When a spine is first selected, all five analysis values default to **No** and the defaults are persisted. The reviewer should actively change any category to **Yes** when a defect is observed.

Button styling provides an additional visual cue:

- **Yes** uses the warning style;
- **No** uses the success style;
- the currently stored choice remains highlighted after navigation or restoration.

![Placeholder: five spine defect-analysis rows with Yes/No choices](docs/images/placeholder-defect-analysis.png)

## 7. Validity classification

After reviewing the five defect categories, classify the spine with one of two buttons:

- **Valid:** the spine has no identified defects;
- **Invalid:** at least one defect is present.

The interface enforces the following rule:

- **Valid** is enabled only when all five defect categories are set to **No**.
- **Invalid** is enabled only when at least one defect category is set to **Yes**.

If a defect is marked **Yes**, the spine cannot be marked Valid. The reviewer must still click **Invalid** to record the classification and advance to the next spine.

This prevents accidental classifications while keeping the defect details and final validity decision as separate pieces of recorded information.

![Placeholder: Valid and Invalid buttons showing their enabled/disabled states](docs/images/placeholder-validity-buttons.png)

## 8. Automated navigation sequence

The intended review sequence for each section is:

```text
Select section
    ↓
Inspect complete section against source mesh
    ↓
Choose Missing Spines or No Missing Spines
    ↓
First spine is focused automatically
    ↓
Review five defect categories
    ↓
Choose Valid or Invalid
    ↓
Next unvalidated spine is focused automatically
    ↓
Repeat until every spine in the section is classified
    ↓
Next spiny section is selected automatically
```

### 8.1 Next Spine behavior

After a spine is classified, **Next Spine** searches forward for the first unvalidated spine and wraps to the beginning of the current section when necessary.

The button is disabled when the current explicitly selected spine has not yet received a validity decision. This prevents the reviewer from skipping a spine accidentally.

If all spines in the current section are classified, the next-section behavior is triggered. When the final spiny section is complete, navigation wraps to the first spiny section.

### 8.2 Manual navigation

Manual navigation remains available for rechecking previous decisions:

- **Prev Spine** moves backward, wrapping within the section;
- the spine dropdown jumps directly to a loaded spine;
- **Prev Section** and **Next Section** move between spiny sections; and
- the section dropdown jumps directly to a section.

Changing a previous analysis or validity result schedules a new CSV save.

![Placeholder: navigation sequence showing automatic movement from one spine to the next](docs/images/placeholder-automatic-navigation.png)

## 9. Progress and analysis tables

The status area reports both local and global progress.

### Current section status

The current status includes:

- current section ID and position in the spiny-section list;
- current spine position within the loaded section;
- current spine validity (`Valid`, `Invalid`, or `Not Set`);
- whether the section is complete; and
- the number of classified spines out of the expected section count.

### Overall status

The overall status includes:

- completed sections out of all sections containing spines; and
- completed spines out of all spines in spiny sections.

The statistics area displays two tables:

1. **Current Section Analysis** — details for the selected section.
2. **Mesh Analysis Summary** — one row for every section containing spines.

The tables include:

- section ID;
- number of spines;
- whether the section is fully validated;
- remaining spines;
- counts for all five defect categories; and
- the missing-segmented-spines decision.

Status colors are used in the tables:

| State | Color meaning |
| --- | --- |
| Complete/validated | Green |
| Incomplete progress | Amber or orange |
| Missing segmented spines | Red |
| No missing segmented spines | Green |
| Section decision not set | Gray |

## 10. Visualization colors and background modes

The viewer uses color to separate mesh context, morphology sections, spine identity, selection, and status.

### 10.1 3D visualization colors

| Object | Default color/appearance | Purpose |
| --- | --- | --- |
| Global mesh context | Light cyan, `0x87CEEB`, 45% opacity | Provides the broad source-mesh context. A deterministic 15% vertex sample is shown. |
| Selected section mesh cloud | Blue, `0x2F80ED`, 80% opacity | Shows the full-resolution local mesh region around the selected section. The section query is expanded slightly to avoid clipping boundary vertices. |
| Unselected morphology centerlines | Gray, `0x888888` | Provides structural context for the morphology. |
| Selected section centerline | Red, `0xFF0000`, thick line width | Identifies the section currently under review. |
| Selected section centerline on black | Hot red, `0xFF1744` | Maintains contrast against a black background. |
| Spine meshes | Deterministic saturated palette excluding blue/cyan hues | Keeps individual spines visually distinguishable from the mesh context. |
| Unselected spines after spine focus | Gray, `0xA0A0A0` | De-emphasizes other spines while preserving the selected spine’s palette color. |
| Selected spine | Its assigned saturated palette color plus a red bounding box | Makes the selected object easy to identify without changing its identity color. |
| Spine bounding box | Red, semi-transparent | Shows the bounds used for selection and camera focus. |

The spine palette is deterministic and based on a golden-angle hue sequence. Blue and cyan hues are intentionally reserved for the source-mesh point clouds.

### 10.2 White and black backgrounds

The default plot background is white. Use **Black Background** when a dark presentation gives better contrast for a particular mesh or spine configuration.

When the background changes to black:

- the plot background becomes `0x000000`;
- the base centerlines change to a lighter gray;
- the active section centerline changes to hot red; and
- the toggle label changes to **White Background**.

Click the button again to restore the white background and the default line colors.

## 11. Screenshots and visual evidence

### 11.1 Taking a screenshot

Use the **ScreenShot** button to capture the currently rendered K3D canvas. The capture uses the live WebGL canvas, preserving the current camera, colors, projection, background, visible geometry, and bounding box.

A screenshot can be taken when:

- a section is loaded and the section-level view is being reviewed; or
- an individual spine is selected for detailed assessment.

The screenshot control is temporarily disabled while a capture is being requested and written to disk.

### 11.2 Screenshot naming

Screenshots are saved in the proofreading directory beside the input mesh. The directory is created automatically:

```text
<mesh_stem>_proofreading/
```

Section-level screenshots use:

```text
section_<section_id>_<sequence>.png
```

Spine-level screenshots use:

```text
section_<section_id>_spine_<global_spine_id>_<sequence>.png
```

The sequence number is automatically incremented for the relevant section or section/spine pair.

Examples:

```text
section_12_1.png
section_12_2.png
section_12_spine_245_1.png
section_12_spine_245_2.png
```

### 11.3 Recommended screenshot points

For a complete visual record, consider capturing:

1. one section-level image after loading the section and before focusing a spine;
2. one image for each spine with a visible defect;
3. one image for ambiguous or borderline cases; and
4. one final overview image after completing a group of sections.

## 12. Persistence and validation CSV

Validation changes are saved asynchronously so that the notebook interface remains responsive while the reviewer navigates the viewer.

The proofreading directory and CSV are created using the input names:

```text
<mesh_stem>_proofreading/
└── <morphology_stem>_validation.csv
```

The current CSV format contains two tables:

### Section table

The section table records:

- `Section`;
- `Number Spines`;
- `Validated (Yes or No)`;
- `Remaining Spines to Validate`;
- `False Positives`;
- `Incomplete Spines`;
- `Falsely Extended`;
- `Merged Spines`;
- `Split Spines`; and
- `Missing Segmented Spines`.

### Spine table

The spine table records:

- `Section ID`;
- `Local Spine ID`;
- `Global Spine ID`;
- `Validity`;
- `False Positive`;
- `Incomplete Spine`;
- `Falsely Extended`;
- `Merged Spine`; and
- `Split Spine`.

The writer uses a temporary file and atomic replacement when updating the CSV. This reduces the risk of leaving a partially written validation file if the notebook is interrupted during a save.

On startup, the validator restores the existing CSV. Legacy schema-1 validation files are migrated to the current schema when possible.

## 13. Generate Report button

Click **Generate Report** to create an analysis PDF without uploading or registering the assessment.

The report sequence is:

1. wait for pending validation data to finish writing;
2. wait for the latest screenshot to finish writing, if applicable;
3. load the report-generation helper;
4. generate the analysis PDF using the current validation CSV and proofreading images; and
5. display **Report Generated** or an error message.

The analysis PDF is written to the proofreading directory. The exact filename is generated by the report helper and should end in `_analysis.pdf` for registration compatibility.

## 14. Register button

Click **Register** to save the current validation state and upload the assessment package.

### 14.1 Registration sequence

The registration process displays four stages:

```text
1/4 Saving validation data
2/4 Generating analysis artifacts
3/4 Staging analysis data
4/4 Registering file
```

Detailed behavior:

1. **Save validation data** — waits for pending asynchronous CSV writes and ensures a current CSV exists.
2. **Wait for screenshot** — waits for the most recent screenshot write when a capture is still pending.
3. **Generate analysis artifacts** — creates the analysis PDF from the current CSV and screenshots.
4. **Stage analysis data** — creates a timestamped, user-specific destination directory.
5. **Create the registration archive** — stages the validation CSV and analysis PDF.
6. **Upload/register** — calls the configured upload helper and reports success or failure in the notebook.

The registration directory is identified using the mesh ID, authenticated user, and UTC timestamp, following a pattern similar to:

```text
<mesh_id>_<user>_<YY.MM.DD_HH.MM>/
```

The archive is intended to contain the validation CSV and analysis PDF. The uploader sends the resulting package to the configured `archives` destination.

### 14.2 Register button behavior

- The button is disabled while registration is running.
- It is re-enabled after success or failure.
- The interface does not currently block registration when sections or spines remain unvalidated.
- A failed upload or report-generation error is displayed in the registration status area and printed to the notebook output.

## 15. Complete reviewer checklist

Before registering a completed assessment, verify that:

- [ ] the correct OBI project is selected;
- [ ] the correct EM dataset is selected;
- [ ] the morphology corresponds to the source mesh;
- [ ] every section listed in the section dropdown has been reviewed;
- [ ] every section has a **Missing Spines** or **No Missing Spines** decision;
- [ ] every displayed spine has a **Valid** or **Invalid** decision;
- [ ] all observed defect categories are recorded correctly;
- [ ] the progress counters show all expected sections and spines as complete;
- [ ] screenshots have been captured for defects or ambiguous cases where evidence is needed;
- [ ] the report has been generated successfully; and
- [ ] the registration status confirms a successful upload.

Because incomplete registration is currently allowed, the reviewer must use the progress counters and checklist rather than relying on the Register button being disabled.

## 16. Troubleshooting

### The morphology dropdown is empty

The selected EM dataset may not have accessible derived morphologies for the current project. Select another dataset or run the skeletonization workflow first.

### Manual morphology selection does not work

Confirm that `neuron_id` contains the OBI platform morphology ID, not a `pt_root_id`, a local filename, or a mesh ID. In manual mode, `download_data()` reads the notebook-level variable.

### The validator cannot find the input files

Check that both paths passed to `validate_spines()` exist and that the HDF5 morphology and GLB mesh belong to the same neuron/source reconstruction.

### The viewer does not show a local section mesh

The local mesh point cloud is queried from the source mesh using the selected section bounds. Confirm that the source mesh is the expected mesh and that the morphology and mesh use compatible coordinates/scaling.

### Existing progress was not restored

Check the proofreading directory beside the mesh and confirm that the expected file exists:

```text
<mesh_stem>_proofreading/<morphology_stem>_validation.csv
```

If the CSV is malformed or belongs to a different source morphology, the validator reports the restoration problem and may start with a fresh in-memory state.

### Screenshot capture fails

Confirm that the K3D widget has rendered in the notebook frontend. Retry after the viewer is visible. The screenshot is taken from the live WebGL canvas, so a non-rendered or disconnected widget cannot provide an image.

### Report generation or registration fails

Inspect the notebook output and status label. Confirm that:

- the validation CSV is writable;
- the proofreading directory is writable;
- the report helper and fonts are available;
- the generated PDF has an `_analysis.pdf` suffix; and
- the configured registration uploader is available and authenticated.

## 17. Reproducibility and output locations

For each assessment, keep the following together:

```text
<mesh_stem>.glb
<morphology_stem>.h5
<mesh_stem>_proofreading/
├── <morphology_stem>_validation.csv
├── section_<section>_<sequence>.png
├── section_<section>_spine_<global_spine>_<sequence>.png
└── <mesh_stem>_analysis.pdf
```

The exact report filename may be produced by the report helper, but it must be an analysis PDF compatible with the registration stage.

When sharing or archiving an assessment, include the source identifiers, the validation CSV, the analysis PDF, and any required visual evidence according to the project’s data-management policy.
